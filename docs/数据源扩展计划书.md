## 0.5 视角校准：这是**基金**项目，不是股票项目

> 股票是「一级」资产，基金是「二级」——基金是**包装**。这个判断直接决定哪些数据源有价值。

### 0.5.1 两个资产类别的成本结构根本不同（实测证据）

**实测**：`backtest.py:554-565 _monthly_returns()` 用 `get_fund_nav(...)["unit_nav"]` —— 即**基金公布的单位净值**。

而基金费率页明确写着（007029 实测原文）：

> 管理费、托管费、销售服务费**从基金资产中每日计提。每个交易日公告的基金净值已扣除**管理费和托管费，**无需投资者在每笔交易中另行支付**。

**但 `backtest.py:509-512` 又扣了一次管理费**：

```python
509:  decay = (1 - self.cost.management_rate_annual() / 12)      # management_fee_annual = 0.015
510:  portfolio_value *= (1 + port_ret / 100) * decay
512:  h["value"] *= (1 + rets.get(h["code"], 0.0) / 100) * decay
```

→ **管理费被重复计费**。对股票这不成立（股价不含管理费）；对基金，净值本身就是**费后序列**。

**量级**：1.5%/年，5 年回测 ≈ 累计低估 **7.2%**；7.5 年 ≈ **10.7%**。

**⚠️ 关键：这个重复计费是「修好 B1 之后才被激活的」。**
- B1 之前：`strategy_monthly.append(ret)` 存**毛收益**，而 `portfolio_value`（扣了管理费）**被丢弃** → 管理费**不影响任何指标**（当时审计的原话是"管理费只扣在一个没人用的变量上"）
- B1 之后：`strategy_returns[next_m] = portfolio_value / pv_start - 1` → 管理费**真的进指标了**
- **结论：B1 修对了一个 bug，同时激活了另一个。**

**同类问题**：`backtest.py:45 purchase_fee = 0.0015`（0.15% 申购费），而实测持仓 **7/7 全是 C 类份额**，C 类**申购费 = 0%**（费率页实测：007029 最高申购费率 `0.00%`）。→ **买入成本被系统性高估**。

> **这是「一级 vs 二级」最具体的体现**：同一套成本模型不能跨资产类别复用。基金/股票的成本建模逻辑必须分开。

### 0.5.2 基金层的「一级」变量是**外壳属性**，不是个股基本面

| 基金层一级变量 | 为什么是决定性的 | 项目现状（实测） |
|---|---|---|
| **费率**（申购/赎回/管理/托管/销售服务） | 对基金是**主导性**连续成本，直接吃掉收益 | `mgt_fee` 全库仅 46% 有真值（14,367 只为 `0.0` 哨兵）；`custodian_fee`/`purchase_fee`/`redeem_fee` **0% 填充** |
| **规模** | 太小 → **清盘风险**（股票没有的资产特有风险）；太大 → 容量约束 | `fund_size` **2.0%** 填充；持仓 7 只**全为 None** |
| **基金经理 + 任职年限** | 历史净值可能属于**上任经理** → 业绩不可归属 | `manager_tenure` **0%** 填充 |
| **公告事件** | 限购、清盘、转型、经理变更、费率调整 = 基金的"公司行动" | 无接入（`sentiment_monitor` 走 akshare，见 §1.1） |
| **份额类别**（A/C/E） | 决定费率结构与最短持有期 | 有 `fund_name` 可推断，但未被用于费率判断 |

### 0.5.4 股票层信息对基金项目的**正确用法**

不是用来选股，而是**穿透验证**：

| 用途 | 说明 |
|---|---|
| **伪分散检测** | 买 3 只"不同"基金，若底层重仓高度重叠，分散是假的。这是纯基金层问题 |
| 风格漂移 | 名义"创新成长"，实际重仓半导体 → 与你的板块暴露判断冲突 |
| **⚠️ 你的持仓有硬限制** | 7 只**全是指数/联接基金**，其"持仓"是所持 ETF，**穿透一层仍是指数**。要做股票层暴露需**两层穿透** |

**结论**：持仓穿透的**唯一有价值的落地形态是"基金间重叠度检测"**，而不是"看基金买了哪些股票"。前者回答"我的分散是不是假的"，后者对你的决策没有增量。

### 1.2 ⚠️ 同花顺净值与本地 DB 曾经的"952 天不一致"**是我自己的时区错误**

必须记录这个排查过程，因为它正好演示了双源校验的价值：

- 第一轮对比：957 个重叠日里 **952 天不一致，最大差 0.0979** → 看起来像严重数据问题
- 假说一：同花顺日期滞后一个交易日 → **被否定**（一致率仅 0.5%）
- 真正原因：同花顺返回的 `nav_date` 是**北京时间零点的毫秒时间戳**（`1788451200000` → 北京时间 `2026-09-04 00:00`），而我用 `pd.to_datetime(ms, unit='ms')` 按 **UTC** 解码，得到 `2026-09-03`

**按 `Asia/Shanghai` 正确解码后**：

```
  007029  重叠 1215  一致(<1e-6) 1215 (100.0%)  最大差 0.000000
  014143  重叠 1171  一致(<1e-6) 1171 (100.0%)  最大差 0.000000
  018392  重叠  754  一致(<1e-6)  754 (100.0%)  最大差 0.000000
```

**同花顺净值数据完全正确**，与本地 DB（源自 akshare）逐点一致。

**这正是"净值必须双源校验"的直接证据**：单源时，这类时区/日期错位错误会**静默入库**，而它污染的正是你的 T+1 计价、`effective_apply_date`、日收益率和全部回测。

### 1.3 🔴 顺带发现项目真实隐患：`ms_to_date` 依赖机器时区

`src/data/hithink_collector.py:417-423`：

```python
@staticmethod
def ms_to_date(ms: int) -> str:
    """毫秒时间戳 → 日期字符串"""
    try:
        return datetime.fromtimestamp(ms / 1000).strftime("%Y-%m-%d")
```

`datetime.fromtimestamp()` 使用**本机时区**。实测：

```
本机时区: ('中国标准时间', '中国夏令时')  UTC 偏移: +8.0
原始 ms: 1788451200000
  datetime.fromtimestamp(ms/1000)  -> 2026-09-04   ← 本机(UTC+8)恰好正确
  utc 解码                         -> 2026-09-03   ← 错误
  正确(北京时间零点)                -> 2026-09-04
```

**本机是 UTC+8，所以现在是对的。但部署到 UTC 服务器（或 Docker 默认 UTC）上，所有净值日期会整体早一天。**

这与 TradingAgents 记录过的同类问题完全一致（其 `#1126`：*host-local timestamp parsing made filtering machine-dependent*）。

**修法**：显式指定时区，不依赖机器设置。

```python
from zoneinfo import ZoneInfo
_CN = ZoneInfo("Asia/Shanghai")
return datetime.fromtimestamp(ms / 1000, tz=_CN).strftime("%Y-%m-%d")
```

## 4. 建议方案：分工 + 双源校验

### 4.1 结论：**不要二选一，也不要双写；按类型分工 + 净值交叉校验**

理由：
1. **同花顺净值只有 5 年**，做净值主源会截断历史 → 不可接受
2. **同花顺有 akshare 拿不到的结构化字段**（`manager_tenure`、`trade_rule`、`rate_info`）→ 有价值
3. **净值是账务地基**，单源静默出错无法发现（§1.2 已实证：我自己的时区错误差点被当成"同花顺数据有问题"）
4. **双写会互相覆盖**，产生"同一字段不同源"的隐蔽不一致

### 4.2 分工表

| 数据类型 | 主源（写入） | 校验源（只读比对 + 告警） | 理由 |
|---|---|---|---|
| **基金净值历史** | **akshare** | **同花顺** | akshare 覆盖完整；同花顺做逐点校验 |
| 基金名录 | akshare | — | 27843 行，无替代 |
| **基金资料 / 费率 / 经理** | **同花顺** | 东财 jbgk | 结构化，字段最全 |
| `benchmark` 字段 | 东财 jbgk | — | 只有它有 |
| **持仓穿透** | **同花顺** | 东财 F10 | 结构化 JSON，字段更全 |
| 指数历史 / 快照 | **同花顺** | 东财 push2 | 官方 API + 批量 |
| 交易日历 | akshare（日历） | 同花顺 `trade_rule`（15:00 切点语义） | 各取所长 |
| **基金公告（消息面）** | 东财 JJGG API | — | 同花顺无此能力 |
| 市场快讯（消息面） | 新浪 7x24 | 华尔街见闻 | 财联社已失效 |

### 4.3 双源校验的具体设计

**不要**做成"A 失败就用 B"的静默回退 —— 那只会掩盖问题。要做成**显式比对 + 可见告警**：

```
采集净值时：
  1. 主源 akshare 写入 fund_nav
  2. 校验源同花顺取同一区间的 NAV
  3. 逐点比对：
     - 完全一致（<1e-6）        → 静默通过
     - 差异 < 0.5% 且日期集合一致 → 记 warning，写入校验日志
     - 日期错位 / 缺失            → 记 error，**不覆盖主源数据**，前端展示告警
  4. 校验结果落一张 nav_verify 表（或复用 analysis_snapshot）
```

**必须校验的边界**：
- **时区**：同花顺 ms 一律按 `Asia/Shanghai` 解码（§1.3）
- **日期集合**：比 "值是否相等" 更重要的是 "日期是否对齐" —— 本次实验里，错位正是通过日期对齐才暴露的

## 7. 风险与注意事项

**解析脆弱性**：东财 `FundArchivesDatas` 返回 `var apidata={ content:"<div class='box'>…" }` —— **JS 字符串里嵌 HTML**，不是 JSON。必须剥外壳再解析，且必须写 schema 断言测试（xalpha 的 AGENTS.md 里专门有一条：*Never Break the DataFrame*）。**同花顺是结构化 JSON，优先用它**。

**限流**：`pingzhongdata` 就是被限流打死的例子（首测 291KB、之后恒 0 字节）。**加请求间隔，别并发轰炸**。

**HTTP 200 ≠ 有数据**：本次 22 个端点里 4 个是"假 200"。**新增采集必须断言内容形状**。

**ToS**：东财/新浪/腾讯这些都是网页抓取。保持项目现有 curl/requests 方式，遵守合理频率。

**前提时效性**：§1.1 的"Python 可出网"结论**有时效性**。实施时应先跑连通性自检，不要把本文档当作永久事实。

**许可证**：本文档涉及的均为数据接口调用，不涉及代码复用。前一份文档《外部参考整合方案与任务书》里的 GPL-3.0 / 无许可证项目禁拷贝结论仍然有效。

## 8. 通用化路线（范围扩大：不只为本人持仓服务）

> **需求**：当前持仓以 ETF/指数联接基金为主，但未来不限于 ETF；系统不应只为单个用户设计，目标是"大家都能用"的通用基金分析工具（不一定上线）。

### 8.1 结论先行：瓶颈是**数据覆盖**，不是代码抽象

直觉上"扩大市场面"是个架构问题。**实测数据否定了这个直觉** —— 真正的瓶颈是净值采集覆盖率。

### 8.2 实测：`fund_nav` 只覆盖全市场 **0.8%**

```
类型                        基金数    有净值   acc非空    净值行
混合型-偏股                   5735      194    331042    331042
指数型-股票                   5588       12     11700     11700
债券型-长债                   2785        1       735       735
混合型-灵活                   2270        5     10309     10309

混合型-偏债                   1466        0         0         0
债券型-中短债                 1178        3      5481      5481
股票型                       1047        2      2556      2556
货币型-普通货币                969        0         0         0

QDII/FOF/Reits 等              其余        0         0         0
```

**汇总**：
- 有净值的基金 ≈ **218 只 / 27,852 只 = 0.78%**
- **债券类 7,351 只 → 仅 4 只有净值**
- **货币型 969 只 → 0**
- **FOF 1,339 只 → 0**
- **Reits 94 只 → 0**
- 即便在"有净值"的类型里也极少：混合型-偏股 5,735 只中只有 **194 只**（3.4%）；指数型-股票 5,588 只中只有 **12 只**

原因：现有采集只为 `vol_predictor` 的候选池（约 30 只）与实际持仓抓净值，**从未做过全市场采集**。

> **含义**：现在整套系统（温度计、评分、推荐、板块、ML、回测）都建立在**约 220 只基金的净值**上。要"扩大市场面"，**第一步是采集，不是重构**。任何抽象设计在 0.8% 覆盖率下都无法验证。

### 8.3 硬差异：**货币基金根本没有"单位净值"**

实测：货币基金的 `fund_nav` 行数为 **0**，且抽样确认无数据。

这不只是"没采集"，而是**口径不兼容**：

| 资产类别 | 收益表达方式 | 现有 schema 是否适用 |
|---|---|---|
| 股票/混合/指数/QDII | 单位净值 `unit_nav` + 累计净值 `acc_nav` + 日增长率 | ✅ |
| **货币基金** | **每万份收益** + **七日年化收益率**（每日结转份额，净值恒为 1 元） | ❌ **不适用** |
| 债券基金 | 单位净值（有，但分红频繁 → `acc_nav` 差异大） | ⚠️ 部分 |
| 场内 ETF/LOF | 行情价（另有 IOPV），非申赎净值 | ❌ 不同口径 |
| Reits | 净值 + 分派率 | ⚠️ 需扩展 |

**货币基金需要新表**（如 `money_fund_yield`：`fund_code, date, wfsy, qrnh`），或在 `fund_nav` 加口径标识列。**这是一个 schema 变更，不是配置调整。**

### 8.5 成本模型是 **C 类份额特化**的

```python
vol_predictor.py:92   ONE_WAY_COST = 0.005   # 单边成本 0.5%（场外C类/ETF联接口径）
backtest.py:45        purchase_fee = 0.0015  # 申购费 0.15%
factor_test.py:734    "单边0.5%，模拟场外C类份额或ETF联接的实际成本"
```

对以下类别**全都不成立**：

| 类别 | 真实成本结构 | 现有假设的偏差 |
|---|---|---|
| A 类（前端收费） | 申购费 0.1~1.5%（按金额分档）、赎回费按时长分档 | 严重低估 |
| 货币基金 | 申赎费 **0**，但有销售服务费 | 高估 |
| 场内 ETF/LOF | 券商佣金（万分之几），**无申赎费** | 严重高估 |
| 债券基金 | 申购费低、赎回费档位不同 | 高估 |
| FOF | **双重收费**（母基金 + 子基金） | **严重低估** |

### 8.6 温度计的适用边界

现有温度基于 **沪深300 / 中证500 / 上证50 的 PE/PB 分位**。对以下类别**完全无效**：

| 类别 | 应有的"温度"口径 |
|---|---|
| 债券基金 | 10Y 国债收益率分位、信用利差分位 |
| 货币基金 | 7 日年化 / DR007 / 资金面松紧 |
| QDII（纳斯达克/标普） | 对应海外指数估值 + 汇率 |
| Reits | 分派率（分红/价格）相对无风险利率的溢价 |
| 黄金/商品 | 实际利率、金价相对均线 |

`strategy_engine.py:48-52` 已有 `hot → ["债券型", "混合型"]` 的降级逻辑，但**温度本身仍只是 A 股权益估值** → 用 A 股温度决定债券基金的仓位，逻辑上不成立。

### 8.7 「多用户」与「资产类别通用」应当拆开

这是两个独立的问题，成本差一个数量级：

| | 资产类别通用 | 多用户 / 多组合 |
|---|---|---|
| 影响面 | 采集、schema、成本模型、温度、评分 | 数据模型 + 鉴权 + 隔离 |
| 成本 | 中（分阶段，每类可独立落地） | 高（全表加 user 维度 + 权限体系） |
| 实测障碍 | `fund_nav` 覆盖率 0.8%（§8.2） | `investment_plans`/`dca_plans` 均 **1 行**、`holdings`/`transactions` **无 user/account 字段** |
| 对"大家都能用"的贡献 | **决定性** | 间接 |

**建议：优先做资产类别通用，多用户按"本地单用户安装"绕过。**

理由：
1. 数据源是**各机自抓**（东财/新浪/同花顺），没有共享后端可复用
2. 隐私上更安全 —— README 已有"真实计划隐私说明"，说明作者本人也在意这点
3. 通用性体现在**"同一个程序能处理任意基金的任意类别"**，而不是"一个服务承载多个账户"
4. 本地 SQLite 单文件应用天生适合"每人一份"

→ 即：**"大家都能用" = 零配置适配任意基金 + 任意资产类别**，而非多租户。

### 8.8 建议的抽象方向：把散落的 `if "股票" in ftype` 收成一张**类别画像表**

不要在每个模块里判断类型，而是定义一份显式契约，各模块**读契约**：

```
FundClassProfile（按 fund_type 映射）
├─ equity_ratio_range        权益占比区间（用于仓位口径，取代 6 处硬编码集合）
├─ nav_schema                净值口径：unit_nav | money_yield | market_price
├─ confirm_lag_days          确认周期：T+1 | T+2(QDII) | T+0(场内) | T+1(货币)
├─ fee_structure             申购费/赎回费/销售服务费/佣金 + 份额类别规则
├─ valuation_proxy           估值锚：hs300_pe | gov_bond_10y | money_rate | overseas_index | cap_rate
├─ lookthrough_target        穿透目标：stock | fund(FOF) | etf_then_stock | bond
└─ thermometer_applicable    温度是否适用（不适用则明确声明，而不是给个错的值）
```

这与 §0.5 的结论一致：**温度计在数据缺失时应声明 `degraded_dimensions`，而不是静默填 50.0** —— 同一原则适用于"类别不适用"：**声明不适用，而不是硬套 A 股温度。**

### 8.9 通用化分阶段建议

> 全部为**计划**。**前置条件**：§8.2 的覆盖率必须先提升，否则每阶段都无法验证。

| 序 | 事项 | 为什么这个顺序 |
|---|---|---|
| G0 | **扩充净值采集到多类别样本**（先各类型 50~100 只，不求全市场） | 没有数据，抽象无法验证 |
| G1 | 抽 `FundClassProfile`，替换 §8.4 的 6 处硬编码集合 | 纯重构，可立即用现有数据回归验证一致性 |
| G2 | 成本模型按 `fee_structure` 驱动（修 §8.5） | 依赖 G1 |
| G3 | 货币基金口径支持（新表或口径列） | **schema 变更**，需快照 |
| G4 | 温度按 `valuation_proxy` 分派（修 §8.6） | 依赖 G1，且需要债券/货币的宏观数据源 |
| G5 | 多组合/多用户（**或**明确记录为"本地单用户"设计决策） | 见 §8.7 建议 |

**G0 与 G1 可并行**，且 G1 不依赖新数据 —— 它是整个通用化里**性价比最高的一步**。

### 8.10 通用化对已定计划的排序影响

| 原计划项 | 是否需要调整 |
|---|---|
| 阶段 0 成本模型修正 | **融合**：修管理费重复计费时，顺手改成 `fee_structure` 驱动（即 G1+G2） |
| 阶段 1 补齐 `fund_info` | **提升**：`fund_info` 是 `FundClassProfile` 的数据基础，且当前 8 个空字段已造成 3 项实际损失 |
| 阶段 3 持仓穿透 | **调整定位**：`lookthrough_target` 表明穿透目标**因类别而异**（FOF→基金、联接→ETF→股票），不只是"重叠度检测" |
| 新增 G0 采集扩充 | **新增**，且优先级仅次于阶段 0 |
