## 0. 结论速览

| 问题 | 答案 |
|---|---|
| 能把基金量放到全部采集吗？ | **能。** 实测单只净值 0.34~0.9s，全市场 24,054 只历史回填约 **5.3 小时**（仅净值）/ **10.4 小时**（含详情） |
| 磁盘够吗？ | ✅ D: 盘剩余 **165 GB**；全量后 DB 约 **2~4 GB**（现 147 MB） |
| 最大惊喜 | **日常增量只需 1 次请求（约 10 秒）** 就能覆盖全市场——`fund_open_fund_daily_em()` 一次返回 24,054 只的**单位净值 + 累计净值 + 申购状态 + 手续费** |
| 最大的坑 | `insert_nav_batch` 用的是 **`INSERT OR IGNORE`** → 重复采集**只补新行、永不修正历史行**（好处：断点续采安全；坏处：历史坏行修不掉） |
| 建议 | **分三步**：① 全市场当日快照（10 秒，立刻见效）② 权益类 12,690 只历史回填（约 2.8h）③ 按需补详情。**不建议一次性全量** |
| 对 ML 的意义 | 横截面 **588 → 24,054（×41）**，直接解决《ML 可行性研究》里"样本太小撑不起 ML"的最大瓶颈 |

## 1. 实测数据（本轮真机测量）

### 1.1 接口吞吐

| 接口 | 返回 | 耗时 | 说明 |
|---|---|---|---|
| `ak.fund_open_fund_daily_em()` | **24,054 行** | **9.5~11.0s** | 全市场当日净值快照（含累计净值/申购状态/费率） |
| `ef.fund.get_quote_history(code)` | 2,756~5,376 行 | **0.34~0.90s** | 单只历史净值（**含累计净值** ✓） |
| `ak.fund_open_fund_info_em()` | 同上 | 0.59~3.25s | akshare 兜底路径（较慢） |
| `ak.fund_individual_basic_info_xq()` | 14 字段 | **0.54~0.56s** | 单只详情（规模/经理/成立日） |

### 1.2 关键列（决定架构）

`fund_open_fund_daily_em()` 返回列：

```
基金代码 | 基金简称 | {T-1}-单位净值 | {T-1}-累计净值 | {T-2}-单位净值 | {T-2}-累计净值
| 日增长值 | 日增长率 | 申购状态 | 赎回状态 | 手续费
```

→ **这一条接口就能完成"全市场日常增量"**：单位净值 + 累计净值（`nav_series` 需要）+ 申购状态 + 手续费（费率）。
只给最近 **2 个交易日**，所以它**只能做增量，不能做历史回填**。

### 1.3 现有采集机制（为什么要改）

| 命令 | 现状 | 问题 |
|---|---|---|
| `collect` | 抓**全市场列表** → `fund_info`（27,852 条）+ 指数估值 | ✅ 列表已是全量 |
| `nav` | **分层采样**：偏股200 + 混合灵活150 + 股票100 + 指数100 + 债券50 ≈ **600 只** | ❌ 这就是"只有 588 只有净值"的根因 |
| `enrich` | 只为**已有净值**的基金补详情 | 范围被 `nav` 锁死 |

`cmd_nav` **没有** `--limit / --type / --resume` 参数，中断即从头再来。

### 1.4 表结构与幂等性

```sql
CREATE TABLE fund_nav (
    fund_code TEXT NOT NULL, nav_date TEXT NOT NULL,
    unit_nav REAL, acc_nav REAL, daily_return REAL,
    PRIMARY KEY (fund_code, nav_date)      -- ✅ 天然防重
);
-- 另有 idx_fund_nav_date
```

```python
# database.py:498
INSERT OR IGNORE INTO fund_nav ...        # ⚠️ IGNORE 不是 REPLACE
```

**三个推论**：
1. ✅ 重复采集/断点续采**安全**（不会重复行）
2. ❌ **历史行永远不会被修正** —— 这就是 `nav_series` 文档里"42 只仅有个位数坏行（多为早期数据）"修不掉的原因
3. ⚠️ 若基金公司**更正**已发布的净值，现有实现**不会更新**（日常增量也会漏掉这类修正）

## 2. 「全量」的分母到底是什么

| 口径 | 只数 | 说明 |
|---|---|---|
| `fund_info`（名称表） | 27,852 | 含已停售/未成立/清盘 → **不是可采集量** |
| **当日有净值（真实可采集）** | **24,054** | `fund_open_fund_daily_em` 实测 |
| 其中**货币型** ≈ 969 | — | ⚠️ **没有"单位净值"口径**（计划书 §8.3），`fund_nav` schema **不兼容** |
| **可落 `fund_nav` 的有效上限** | **≈ 23,085** | |

按类型（`fund_info` 实测）：

| 类别 | 只数 | 建议优先级 |
|---|---|---|
| 混合型-偏股 | 5,735 | **P0**（筛选/推荐主战场） |
| 指数型-股票 | 5,588 | **P0** |
| 股票型 | 1,047 | **P0** |
| 混合型-灵活 | 2,270 | **P1** |
| 债券型（各类合计） | 7,394 | P2（分红频繁，`acc_nav` 差异大，价值高但口径复杂） |
| 货币 / QDII / FOF 等 | 2,690 | P3（需 schema 扩展） |

→ **权益类合计 12,690 只**，是"投入产出比"最高的目标。

## 3. 代价估算

### 3.1 时间（单线程，实测速率外推）

| 范围 | 只数 | 仅净值<br>(0.8s/只) | 净值+详情<br>(1.55s/只) |
|---|---|---|---|
| 权益类（P0+P1） | 14,960 | **3.3 h** | **6.4 h** |
| 权益类（仅 P0） | 12,690 | **2.8 h** | **5.5 h** |
| 全量（非货币） | ~23,085 | **5.1 h** | **9.9 h** |
| **日常增量（全市场）** | 24,054 | **10 秒** ⭐ | — |

⚠️ **未计限流**。计划书 §2 已实测过"东财 `pingzhongdata` 首测 291KB 成功、之后稳定 0 字节（限流）"。
连续 2 万次请求大概率触发限流 → **实际可能需要 1~3 天**（取决于限速策略）。必须做退避 + 断点续采。

### 3.2 数据体积

当前：**1,220,179 行 / 588 只 / 147 MB**（约 100 B/行，含索引）

| 情形 | 平均行数/只 | 总行数 | DB 体积 |
|---|---|---|---|
| 保守（大量新基金） | 800 | 1,924 万 | **≈ 1.9 GB** |
| 中位 | 1,500 | 3,608 万 | **≈ 3.6 GB** |
| 上限（按现有 588 只的 2,075） | 2,075 | 4,991 万 | **≈ 5.0 GB** |

磁盘 165 GB 剩余 → **空间不是问题**。

### 3.3 对现有模块的性能冲击（必须配套解决）

| 模块 | 现状 | 全量后（线性外推） | 对策 |
|---|---|---|---|
| `FundScreener.screen_funds` | 588 只冷算 **2.8s** | **≈ 2~4 分钟** | ① 候选池先按类型/申购状态 SQL 预筛；② 用 `cmd_precompute` 落 `analysis_snapshot` 缓存 |
| `_load_nav_series` 内存 | 588 只序列常驻 dict | 2.9 千万行 pandas → **数 GB 峰值**（OOM 风险） | 分批读 + 只装候选池，不要全量驻留 |
| Web `/api/funds` | 已优化到 2.8s | 会**超时** | 预计算 + 缓存（Web 端 `QFA_MARKET_LIVE=0`，不能靠实时算） |
| `historical_recommender` | 107 只候选回测 18 个月 | 候选池扩大后线性变慢 | 已用固定种子抽样（批次 4.5），需同步调小 `per_group` |

## 4. 必须先做的 4 项工程改造

| # | 改造 | 为什么必须 |
|---|---|---|
| **1** | **限速 + 指数退避 + 失败清单落 `data_log`** | 2 万次连续请求必触发限流；失败要可重试、可追溯 |
| **2** | **断点续采**：`cmd_nav --resume`（跳过已有净值的 code）、`--limit`、`--type` | 中断即从头再来是不可接受的（`INSERT OR IGNORE` 已让续采天然安全，只差参数） |
| **3** | **评分侧预计算 + 候选池预筛** | 否则 Web 端 2 分钟冷算直接不可用 |
| **4** | **内存分批**：`_load_nav_series` 不常驻全量 | 防 OOM |

**再加一条可选但建议**：给 `fund_nav` 补一条**修正路径**（`INSERT OR REPLACE` 或专门的 `--repair` 模式），
让"历史坏行"可被修正——这是 `nav_series` 文档里悬了很久的问题。

## 5. 建议方案：三步走

### Step 1 ⭐ 全市场当日快照（10 秒，立刻见效，风险极低）—— ✅ 已完成（2026-09-20）

新增 `cmd_snapshot`：调 **1 次** `fund_open_fund_daily_em()`，把 24,054 只的
`T-1/T-2 单位净值 + 累计净值 + 申购状态 + 手续费` 写库。

**立刻获得的收益**：
1. 库内**所有**基金都有最新净值（而不是 588 只）
2. **顺带修掉 Q-A 待办的一半**：费率与申购状态是"当日快照带回来的"，可用来恢复被 `upsert` 清空的字段
3. 每天 10 秒就能保持全市场"当日可见"

**注意**：`INSERT OR IGNORE` → 已存在的行不会被覆盖。若要用它**修正**存量费率，需要走 `upsert_fund_info`（4.2 已实现局部更新语义）而不是净值路径。

#### 5.1 Step 1 落地实测（2026-09-20）

- 实现：`parse_daily_snapshot()`（collector.py 纯函数，可离线测试）+ `cmd_snapshot()`（CLI `snapshot`）；
  `upsert_fund_info` 加 `commit=False` 参数，两万行更新包成一个 `immediate()` 事务。
- 首跑结果：快照日期 **2026-09-17 / 09-18**，**24,103 只**基金，解析 45,365 行、**新增 45,359 行**；
  有净值的基金 **588 → 23,421（×40）**；09-18 当日覆盖 22,721 只。
- fund_info：24,128 只有申购状态、12,987 只有费率（局部更新，空值未覆盖旧值）。
- 持仓基金即时受益：024663 / 017470 / 018392 当日（09-18）净值到手（016453 为 QDII 滞后一天，正常）。
- **日线缺口检测已内建**：快照首日与库内最新日期间若隔交易日，打印缺口清单并提示回填路径。
- 测试：`tests/test_snapshot_parse.py` 6 用例；全测 **323 passed**。
- 回滚点：`data/_snapshot_20260920_185148.db`（首跑前 147 MB 整库快照）。

### Step 2 权益类历史回填（约 2.8~5.5 小时，可分批过夜跑）

`cmd_nav --type 权益 --resume`，只抓净值（详情后置），12,690 只。
跑完 → **ML/筛选/推荐的横截面从 588 → 12,690**。

### Step 3 按需补详情 + 扩类别

- 只为**真正进入候选池**的基金补规模/经理/成立日（现有 `enrich` 加范围参数即可）
- 债券型（7,394 只）价值高但分红频繁，建议等 Step 2 验证稳定后再做
- 货币基金需先做 schema 扩展（计划书 §8.3 的 `money_fund_yield` 新表），**不在本轮**

## 6. 三个必须提前知道的坑

1. **`INSERT OR IGNORE` 只增不改** → 重采不能修历史；如需修复要另设路径（见 §4 可选条）
2. **计划书 §8.4 的"6 处互不一致的权益类定义"**：全量后不一致会被放大 41 倍。
   采集范围的定义**必须复用同一张类别清单**，不要新增第 7 处（可用 `fund_scorer.type_bucket` / 计划书 §8.8 的 `FundClassProfile`）
3. **货币基金 969 只无"单位净值"口径** → 它们**采集了也进不了 `fund_nav`**，不要把它们算进"全量"的收益预期里

## 8. 需要你决策（2026-09-20 双重审计后修订）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 是否接受 DB 涨到 **2~4 GB**？ | ✅ 接受（磁盘 165 GB 充足）——**附带决策 6 的快照策略改造** |
| 2 | **一次性全量** vs **三步走**？ | ✅ **三步走**（Step 1 已落地 ✅；Step 2 须先过闸门，见决策 7） |

| 5 | 详情（规模/经理/成立日）全量还是按需？ | ✅ **按需**：全量 2 万次 ×0.55s 只为 2% 的实际用途，不值 |

| 7 | **Step 2 的前置闸门**（审计修正②，新增） | ⏸ Step 2（权益类 12,690 只历史回填）开工前必须先完成：**(a) 黑箱验收审计**（§9 待办，证明现有 pipeline 可信——pipeline bug 会被 41 倍数据放大）；**(b) L1 ML 基线**在现有 588 只上与 `quality_score` 对打（证明扩数据有地方兑现，防止"为数据而数据"）。依据：ML 可行性研究自证"ML 真实价值=排除差基金"，数据只有被有效模型消费才产生收益 |

**审计结论的优先级排序**（第一性原理）：**可信性 > 覆盖度 > 模型复杂度**。
在 ¥1,300 量级实盘上，一个 pipeline bug 的损失 > 数据覆盖不足的损失（覆盖不足已有 10 秒定向刷新兜底）。
