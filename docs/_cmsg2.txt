fix(前端): 旧仪表盘涨跌色反转 —— 盈利显示绿、亏损显示红（中国惯例应为涨红跌绿）

接手核查时发现的**功能性错误**（非审美）。旧前端 `/` 是用户日常在用的界面，
而新前端 `/v2` 目前只有「今天」一页，退役按计划还要对照跑至少两周 ——
这期间用户每天都会把赚的读成亏的。

== 根因 ==

app.css 原先只有 up/down 一对色，同时承担两种互相冲突的语义：
  (a) 方向：P&L / 收益率 / 累计收益 —— 中国 A 股惯例要 涨红跌绿
  (b) 状态：危险 / 成功 / 预警 / 风险等级 —— 红色=危险是普适的，不能反
而 up/down 取的是欧美惯例（--up:#27a644 绿 / --down:#e5484d 红），
于是 (a) 全部反了。实测 16 处方向取色点，例如：
  app.js:486  (pnl>=0?'var(--green)':'var(--red)')        累计收益为正 -> 绿
  app.js:774  g.pnl>=0?'var(--up)':'var(--down)'          持仓盈利 -> 绿
  app.js:1197 (s.ret_1m||0)>0?'var(--green)':'var(--red)' 近1月上涨 -> 绿

== 修法：拆开语义，不复用 up/down ==

没有交换 --up/--down 的值 —— 那样会把 .btn.danger / .toast.err / .alert-red
这些危险语义一起变绿，更糟。而是新增一对只表示方向的 token：
  --rise:#e5484d（涨=红）  --fall:#27a644（跌=绿）
状态类继续用 --up/--down，语义不变。
命名沿用新前端的 rise/fall —— 其计划书 §1.2 明确指出 up/down 在两种惯例下
颜色相反，这两个名字本身就是事故词源。

改动点：CSS 8 处 + JS 17 处。调仓指令的 买入/卖出 方向色一并纠正
（A 股惯例同为 买入=红/卖出=绿）。

== 顺带发现：这个 bug 被一条测试"保护"着 ==

tests/test_curve_render.py 断言的是欧美惯例，注释原文「零上绿 / 零下红」
「零上面积用绿色（涨）」—— 它把错误惯例当成了预期行为，
于是任何修正都会被它报成"回归"。已按项目定案（计划书 §1.2）改为 rise/fall，
并在注释里写明这次更正的来由。这正是先改代码后被测试拦下的那一次。

== 防回归 ==

新增 scripts/check_rise_fall.py（永久守卫，非一次性脚本）：
  · 三条判据：收益变量与0比较 / 已知方向选择器硬清单 / CSS 方向关键词
  · 同时正向校验 --rise 必须是红色系、--fall 必须是绿色系
  · 状态点单独列出供人工复核，不误报
第一版守卫只靠「变量名+与0比较」的启发式，漏掉了 .u-bgup/.u-bgdown ——
它们没有条件表达式，但注释明写"零轴上方（盈利区间）"，是纯方向语义；
若只改曲线渐变而不改图例，会造成"图例与曲线自相矛盾"。靠人工复核图例文案才发现，
故守卫加强为硬清单断言。

== 验证（实测） ==

  node --check src/web/static/app.js          -> OK
  python scripts/check_rise_fall.py           -> 方向点残留 0，token 语义校验通过
  GET /static/app.css、/static/app.js          -> 服务端已返回修复版
