## 1. 现在的漏洞

`holdings` 只有 `buy`/`sell` 两种流水，**没有分红的入账路径**：

```
transactions.kind 取值:  'buy' 24 / 'sell' 4      ← 没有 dividend
holdings 含 cash/dividend 的列:        []
```

基金现金分红时 **单位净值（`unit_nav`）在除息日向下跳**，而**累计净值（`acc_nav`）不跳**。
本项目的持仓市值 = `份额 × unit_nav`，于是：

- 除息日当天，**总资产凭空少掉一笔分红**（净值下挫，份额没变，现金没入账）；
- 收益率、已实现/未实现盈亏全部跟着失真；
- 真实情况下这笔钱要么**变成新份额**（红利再投），要么**进了银行卡**（现金分红），
  两种都必须记账，否则账不平。

**当前未触发**：实测用户 7 只持仓在全部历史净值上**没有检测到任何除息日**（见 §3），
与任务书"007029 成立来分红 0 次"一致。所以这是**通用化的阻塞项**，不是当下的账目错误。

## 2. 口径定义

| 名称 | 含义 | 本方案如何取 |
|---|---|---|
| 权益登记日 | 这天收盘后持有份额的人有权分红 | 不单独存；**除息日**即可唯一确定一笔分红 |
| 除息日 | `unit_nav` 向下调整的那一天 | 由 §3 检测器给出（就是净值序列上那一天） |
| 每份分红 | `d = Δ(acc_nav − unit_nav)` | 检测器同时给出金额，便于核对 |
| 再投基准日净值 | 红利再投时用来折算新份额的净值 | 默认与除息日同日净值；若数据源另有口径，允许覆盖 |

### 2.1 红利再投（D4 默认）

经济实质：**什么都没发生**。净值下挫的幅度 = 新增份额的价值，总资产与总成本都不变。

```
新增份额 = (持有份额 × 每份分红) / 再投净值
holdings.shares += 新增份额
holdings.buy_amount  不变        ← 没有新增外部投入
holdings.buy_nav     不变        ← 摊薄成本自然下降，这是正确的
```

**为什么成本必须不变**：这笔红利本来就是你已持有资产的一部分（净值里），
把它算成"新增投入"会让收益率凭空变高。
反过来，若除息日**不做**这笔份额补记，则**未来全仓卖出时会少卖**（`record_sell` 用
`holdings.shares` 当持仓上限）—— 这才是漏记再投最实际的后果。

### 2.2 现金分红

```
holdings.shares      不变
holdings.cash_balance += 持有份额 × 每份分红      ← 现金必须有个"家"
总资产 = Σ(份额 × 最新净值) + Σ(cash_balance)
```

- **不是赎回** → 不收赎回费（`portfolio.redeem_fee_rate` 不参与）。
- **不是申购** → 若后续把这笔现金再买回同一只基金，那才是一笔正常的 `buy`，
  按 5.2 的份额公式收申购费。
- 现金是**已实现收益**，不是价差：报表须把"分红收益"与"买卖价差"分开列
  （现有 `get_realized_pnl` 只统计卖出，需扩一列，见 §6）。

### 2.3 可切换（D4）

策略挂在**持仓**上：`holdings.dividend_policy ∈ {reinvest, cash}`，默认 `reinvest`。
挂持仓而不是挂基金，是因为同一只基金在不同时间/不同买入批次可以有不同选择，
而且默认值与基金自身的默认一致（多数基金默认红利再投），**存量行不需要改写**。

## 3. 除息日检测：用已有数据，不出网

`fund_nav.acc_nav`（累计净值）已经入库且**覆盖 99.75%**（1,216,573 / 1,219,617 行），
而 `acc_nav != unit_nav` 有 **423,357 行** —— 分红信息本来就在库里。

```python
# 逐基金按 nav_date 升序；diff_t = acc_nav_t − unit_nav_t
# 非除息日：diff 基本不动（acc 与 unit 同涨同跌，差额恒定）
# 除息日：  unit 下挫而 acc 不下挫 → diff 台阶式上跳，跳幅 = 每份分红
if diff_t - diff_{t-1} > tol:      # tol 建议 1e-4
    候选除息日 = (t, d = diff_t - diff_{t-1})
```

**实测（本机全库跑通）**：587 只有净值的基金里 **244 只**检出了分红候选。

```
000016 华夏纯债债券C   10 次   2024-04-29  unit=1.1228 每份分红≈0.0380
000033 易方达信用债C   26 次   2026-07-23  unit=1.1265 每份分红≈0.0040
000025 大摩双利增强债券C  3 次   2021-08-23  unit=1.0838 每份分红≈0.0802
```

分布完全符合预期（**债券型最多、每次金额很小**），说明检测器可直接用。

**必须承认的两个陷阱**：

1. **份额折算/净值归一化**也会让 `unit_nav` 下挫（不是分红）。二者的差别是：
   分红时"每份分红"就等于 `diff` 的跳幅，而折算时 `unit_nav` 的跌幅
   与 `acc` 的跌幅**相等**（`diff` 不变）→ 本检测器**不会**把折算误判为分红。
   但反向不成立：若某基金 `acc_nav` 本身维护得不规范，会漏检。
2. **金额写错会污染成本与收益**（分红是对**人**的负债）。

### 决策（2026-09-16，用户拍板）：**自动落账，不设人工确认环节**

即检测到的除息日**直接**按 §5 规则入账，不需要人在 UI 上点确认。

因此检测器必须自带**拒收条件**（宁可漏、不可错），三条同时满足才自动落账：

| 条件 | 理由 |
|---|---|
| `diff` 跳幅 > 0 且 **等于** `unit_nav` 当天的跌幅（容差 1e-4） | 排除"份额折算/净值归一化"（那种情况 `diff` 不动） |
| 每份分红落在 `(0, unit_nav)` 内，且当日 `unit_nav > 0` | 排除脏数据（如 acc_nav 被写成 0 或异常跳变） |
| `acc_nav >= unit_nav` | 累计净值不该低于单位净值（低说明该基金数据不可信，整条序列弃用） |

任一不满足 → **不落账**，只在报告里列为"存疑除息日"并给出原始数值，等人工看。

**可审计 / 可回滚**：每笔自动落账都必须把证据写进流水
（`apply_date`、`dividend_per_share`、当日 `unit_nav`/`acc_nav`），
并用 `(holding_id, apply_date, kind)` 做幂等键 —— 重跑检测不会重复入账，
出问题时能按 `apply_date` 一次性撤销。

全自动**无法**覆盖的场景（`acc_nav` 本身维护不规范 → 漏检）本方案不解决，
那需要外部权威分红公告，属《数据源扩展计划书》范围。

## 4. Schema 方案

### 方案对比

| | A：只扩 `transactions.kind` | **B：A + `holdings` 两个新列** | C：单独 `dividends` 表 |
|---|---|---|---|
| 现金有落点 | ✗ 现金分红无处安放 | ✓ `cash_balance` | ✓ |
| 可切换 | ✗ 策略无处存 | ✓ `dividend_policy` | △ 需再加表 |
| 与现有模型贴合 | ✓ | ✓ | ✗ 又多一种账 |
| 改动量 | 最小 | 小（2 列 + 1 个 kind 取值） | 大 |

**推荐 B。**

### DDL（沿用 `_migrate_holdings_t1` 的幂等迁移写法）

```sql
ALTER TABLE holdings ADD COLUMN dividend_policy TEXT NOT NULL DEFAULT 'reinvest';
ALTER TABLE holdings ADD COLUMN cash_balance     REAL NOT NULL DEFAULT 0;
```

`transactions.kind` 是**无 CHECK 约束的 TEXT**，新增取值 `'div_reinvest'` / `'div_cash'`
**不需要 DDL**；另建议加一列审计用：

```sql
ALTER TABLE transactions ADD COLUMN dividend_per_share REAL;   -- 每份分红，便于对账
```

迁移照抄现有做法（`PRAGMA table_info` 判存在 → `ALTER TABLE`，见
`src/data/database.py:381 _migrate_holdings_t1`），幂等、可重复执行。

## 5. 落账规则

```
确认一笔分红（份额 s，每份分红 d，除息日 X，再投净值 nav_r）：
    金额 = s × d
    if dividend_policy == 'reinvest':
        new_shares = 金额 / nav_r
        holdings.shares += new_shares                       # 成本/份额成本不动
        transaction(kind='div_reinvest', apply_date=X, shares=new_shares,
                    amount=0.0, dividend_per_share=d, confirm_nav=nav_r)
    else:  # 'cash'
        holdings.cash_balance += 金额
        transaction(kind='div_cash', apply_date=X, shares=0.0,
                    amount=金额, dividend_per_share=d)
```

- 两者都**不产生外部现金流**（再投）或**不产生基金份额变动**（现金），
  因此 `buy`/`sell` 的定价、T+1/T+2 确认链、赎回费逻辑**全部不受影响**。
- 幂等键：`(holding_id, apply_date, kind)` —— 同一天同一笔只能记一次，
  重跑检测不会重复入账。

## 6. 对现有账务的影响范围（逐点）

| 位置 | 现在 | 加分红后必须改什么 |
|---|---|---|
| `portfolio.get_portfolio_summary` | 总市值 = Σ(份额 × nav) | **+ Σ(cash_balance)**，否则现金分红仍然丢钱 |
| `portfolio._apply_sell` / `record_sell` | 以 `holdings.shares` 为上限 | 无需改（再投已把份额加进去）；**但漏记再投就会少卖** |
| `portfolio.get_realized_pnl` | 只统计 `sell` 流水 | 新增"分红收益"一列，与价差收益分开；两者相加才是总收益 |
| `analysis/rebalance_advisor.py:_holding_value` | 份额 × 净值 | **+ cash_balance**，否则权益占比/调仓金额口径错 |
| `strategy_engine._holding_market_value` | 份额 × 最新净值 | 同上 |
| `web/app.py` 持仓卡 / 总览 KPI | 市值、收益率 | 显示"现金余额"一行；收益率分母口径要写清 |
| `backtest.py` | 见 §8 | 分红不改回测逻辑，但**净值列的选择**要改（见 §8） |
| `dca` 定投 | 无影响 | 分红不是定投期次 |

**不需要动的**：`trade_rules`（T+1/T+2 确认链）、`redeem_fee_rate`（分红不是赎回）、
`fund_scorer` 的门槛（除 §8）、前端赎回费提示。

### 迁移与安全

1. 变更前**完整快照**（`copy data\fund_quant.db data\backups\fund_quant_<时间戳>.db`，
   与 `scripts/backfill_sell_fees.py:88` 同一惯例）；
2. 新列都有 `DEFAULT`，存量 24 行**语义不变**（`reinvest` = 现实默认，`cash_balance = 0`）；
3. **不回填历史分红**（铁律 3）：只让**新除息日**走新规则；历史若确有分红，
   在 UI 上按现有"旧口径"标注方式提示，不静默改写历史账。

## 7. 落地顺序（确认后）

1. 快照 → 迁移两列（幂等）
2. 检测器（含 §3 的三条拒收条件）+ 单元测试：喂真实分红样例必须命中，
   喂份额折算样例必须**拒收**（这是自动落账的安全底线）

   （再投 = 总资产/成本不变；现金 = 总资产不变、现金增加）
4. 在 `nav`/`reconcile` 流程里挂上自动检测入口（新净值落库后顺带跑）
5. 报表三处聚合（总市值、已实现、调仓口径）
6. 前端：持仓行显示策略切换 + 现金余额 + 已实现收益拆分 + "存疑除息日"提示
