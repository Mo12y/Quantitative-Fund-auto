# 深历史采集管道设计与实测

> 生成时间：2026-09-21
> 脚本：`scripts/collect_deep_nav.py`（采集）、`scripts/probe_collect_feasibility*.py`（前置探测）
> 触发：`docs/常量与概念自查报告.md` §2.1 发现「参照系仅覆盖可买池 **2.99%**」

---

## 0. 要解决的问题

```
全市场            27,864
今天可申购         18,677
参照系池(≥3年)        576  ← 仅覆盖可买池的 2.99%
```

**即 97% 的可买基金无法给出同类百分位。** 且「降低历史门槛」实测无效
（`≥1年=589` vs `≥3年=576`，只多 13 只）—— 数据本身只有 576 只有多年历史。

→ 唯一出路：规模化补采集。

---

## 1. 通道选型（实测，非推断）

按 skill **规则 1「数据源验证前置」**，先探测再设计。

### 1.1 三条通道拉「全历史」的耗时（目标基金 007029，1824 条）

| 通道 | 耗时 | 请求数 | 换算 18,677 只（并发 8） |
|---|---|---|---|
| `api.fund.eastmoney.com/f10/lsjz` 分页 | 8.46s | **92 页** | **5.5 小时** ❌ |
| `akshare.fund_open_fund_info_em` | 3.12s | 2 次调用 | 2.0 小时 |
| **`fund.eastmoney.com/pingzhongdata/{code}.js`** | **0.48s** | **1 次请求** | **33 分钟** ✅ |

**关键发现**：`lsjz` 的 `pageSize` 被服务端**硬限制在 20 条**
（传 40/50/100/200 均只返回 20 条；传 ≥500 直接空响应），
1824 条要 **92 页** —— 这条通道被排除。

### 1.2 压力与限流实测

| 测试 | 结果 |
|---|---|
| `lsjz` 500 请求 × workers=24 | 零失败，253 请求/秒 —— **未触发限流** |
| **`pingzhongdata` 400 只 × workers=8** | **零失败，9.4 只/秒** |
| `pingzhongdata` 实跑（含 DB 写入） | 2.9 只/秒 |

> ⚠️ `pingzhongdata` **此前曾被限流**（首次 291KB 成功、之后稳定 0 字节）。
> 本次 400 只持续压力**零失败**，但仍需在正式采集中做失败重试。

### 1.3 选型结论

**通道：`pingzhongdata/{code}.js`** —— 单请求 291KB，含 11 类数据。

## 2. 意外收获：一次请求同时解决 `fund_info` 空字段

`pingzhongdata` 的 27 个 JS 变量中，与 `fund_info` 空字段对应的有：

## 3. 管道设计

### 3.1 风控纪律（逐条对应本项目历史事故）

| 纪律 | 实现 | 对应教训 |
|---|---|---|
| **写库前必须快照** | 脚本启动时检查 `data/_snapshot_*.db` 存在，否则退出 | 铁律 2 |
| **幂等** | `fund_nav` 用 `ON CONFLICT(fund_code,nav_date) DO UPDATE` + `COALESCE` | 重复采集不产生脏数据 |
| **不覆盖已采到的** | `fund_info` 用 `COALESCE(旧值, 新值)` —— **只填空值** | ⭐ **R2 事故**：两条采集路径互相清空字段 |
| **断点续传** | 进度写 `data/collect_progress.json`，中断重跑不重复拉取 | 1.8 小时任务必须可恢复 |
| **时区正确** | `ms_to_date` 显式用 `Asia/Shanghai` | 批次 2.3 同一教训 |
| **可小规模试跑** | `--limit N` | 先验证再全量 |

### 3.2 规模与工期（实测推算）

| 项 | 实测值 |
|---|---|
| 每只平均行数 | **3,311 行**（完整历史，约 13 年） |
| 目标只数 | 18,677（开放申购） |
| **总行数** | **约 6,180 万行** |
| **预计体积** | **约 7.76 GB**（按实测 125.4 字节/行） |
| 磁盘可用 | 156.2 GB ✅ |
| **实测速率** | 2.9 只/秒（含 DB 写入） |
| **预计工期** | **约 1.8 小时** |

**查询性能**：`group by fund_code` 走 `COVERING INDEX sqlite_autoindex_fund_nav_1`
（主键），**大表不会让现有查询退化** ✅

### 3.3 试跑验证（50 只）

```
✓ 快照存在: _snapshot_20260921_083417.db
目标 18,677 只 / 已完成 0 / 本次待采 50
  50/50  成功 50 失败 0  165,565 行  17s  2.9 只/秒
```

**深历史（≥756 天）：576 → 618 只**（+42，约 84% 的样本成为深历史）

## 4. 采集后的验证清单（待执行）

### 4.0 ⚠️ 先纠正一个中途的错误推算

采集启动后我曾用「净值起点 > 2023-09-21 = 新基金」推算，得出
「深历史池上限仅 746 只、96.8% 永远覆盖不到」——
**这个推算错了**：对**尚未采集**的基金，其 `min(nav_date)` 只是 2026-09 快照的起点，
被误判成"成立日"。

**决定性验证**（`scripts/probe_young_or_missing.py`）：随机抽 40 只
「可买 **且** 当前净值点数 <60」的基金，**直接问服务端要全历史**：

| 服务端返回的真实历史 | 只数 | 占比 |
|---|---|---|
| **≥3 年** | **27** | **68%** |
| 1-3 年 | 7 | 18% |
| 3月-1年 | 5 | 12% |
| <3 月（真年轻） | 1 | 2% |

样本明细（证明服务端确实有数据）：
```
163209   3517 点  起点 2012-03-29
001884   2673 点  起点 2015-10-08
005644   2058 点  起点 2018-03-21
006253   1881 点  起点 2018-11-06
017378    930 点  起点 2022-11-24
023835    241 点  起点 2025-08-22   ← 真年轻
027437     36 点  起点 2026-05-22   ← 真年轻
```

**→ 85% 有 ≥1 年历史，「97% 不在参照系」是**采集缺口**而非结构限制。
→ 方案 B 成立。修正预测：深历史池 576 → **约 12,000 只**，覆盖率 2.99% → **约 68%。**

> 这正是 skill **规则 1（数据源验证前置）** 的价值：
> 若当时直接按错误推算否掉方案 B，就会错过一个可解的问题。
> **教训补充**：判断"数据源天花板"时，**不能拿"未采集"的状态当"不存在"** ——
> 必须直接探测服务端。

### 4.1 覆盖率
重新统计「参照系池 / 可买池」比例（目标：从 2.99% 提到约 68%）
### 4.2 参照系重算
`python scripts/calibrate_thresholds.py` —— 样本量从 575 暴增到约 12,000，分位数会变
### 4.3 阈值重新定位
现有 `max_drawdown_1y: 35` 在大样本下的真实百分位
### 4.4 排名稳定性复验
`python scripts/verify_benchmark_stability.py` —— 样本变大后是否仍稳定
### 4.5 `fund_info` 填充率复核
费率 / 经理 / 规模是否被填上（试跑显示 `purchase_fee` 0% → 0.5%，需查解析）
### 4.6 样本分级与同质性复核
类型聚合在新样本量下是否仍成立（`MIN_N_FULL/MID/IQR = 100/50/30`）
