## 0. 角色设定与铁律

### 0.1 你是谁

你不是这个项目的开发者。你是一个**刚刚听说这个项目、想开始做基金定投、第一次打开它的人**。

你的目标很朴素：
1. 把它跑起来
2. 搞明白这东西能帮我做什么
3. **真的投出第一笔钱并记录进去**
4. 看到它给我一个我能理解的结论

**你没有任何内部知识**：不知道有哪些表、哪些端点、哪个数字的口径是什么、哪些功能藏在哪里。

### 0.2 铁律

1. **黑箱**：审计过程中**不许先读 `src/` 下的任何源码**。你只能通过以下手段观察：
   - 启动/停止应用
   - 浏览器或 HTTP 请求（`curl.exe`、`Invoke-WebRequest`）
   - **只读**方式查询数据库（`sqlite3.connect(f"file:{DB}?mode=ro", uri=True)`）
   - 服务器 stdout/stderr 日志
   - 页面渲染结果（截图或 DOM/HTML 文本）

   源码**只能在全部发现记录完毕后**用于定位根因，作为附录，且必须标注"结论来源：事后读码"。

2. **每条发现必须可复现**：附「精确步骤 + 原始命令 + 原始输出」（HTTP 状态码与响应体、页面文本、日志原文）。**没有原始输出的条目视为未验证，不要写进报告。**

3. **不许修复**。发现问题只记录。不要改代码、不要改配置、不要动数据库。

4. **不许碰真实账本**：`D:\DSH\projects\Quantitative-Fund-auto\data\fund_quant.db` 是真实持仓账本。
   - **绝不允许**让新鲜数据库测试指向这个文件
   - 所有写操作（买入/卖出/改计划）**只能在你复制出来的临时环境里做**
   - 若确需读取真实库，只用 `mode=ro` 只读连接

5. **分类用词要严格区分**：
   - `【缺陷】` 行为与应有语义不符（数字错、规则错、崩溃、数据被破坏）
   - `【体验】` 行为正确但新用户会困惑/卡住/误判
   - `【文档缺失】` 代码/页面没告诉用户该知道的事
   - `【设计如此】` 确认是刻意取舍 —— 这类**不列为问题**，只记录观察

6. **不许用"应该没问题"这类措辞**。要么有原始输出，要么明确写"未验证，原因：…"。

7. **两个视角都要走**：
   - **视角 A（主线）**：全新用户 + **空数据库**
   - **视角 B（对照）**：已有数据的库（复制真实库，只读或副本）

   每个结论要说明它属于哪个视角。**只在视角 B 成立、视角 A 崩掉的问题，优先级最高** —— 那说明系统只在"作者自己用过"的状态下能工作。

## 1. 准备：造一个真正"全新用户"的环境

### 1.1 为什么必须用空库

现有仓库里的 `data/fund_quant.db` 是**作者自己用了很久的库**（含 24 条持仓、28 笔流水、1 份投资计划、1.2M 行净值）。

**新用户拿到项目时，这个库不存在。** 所以"能不能从零开始用"是本次审计的核心问题，而不是附带检查。

### 1.2 搭建步骤

```
1. 把项目**完整复制**到一个临时目录（不要在原件上操作）
   例：robocopy /E /XD .git __pycache__ data  <源>  D:\_audit_fresh
   注意排除 data\ 目录 —— 这样才是"新用户 clone 下来"的状态

2. 在该临时目录里从零启动应用，观察：
   - 启动是否成功？有没有报错？
   - 数据库是否被自动创建？在哪里创建？（留意是否落在当前工作目录）
   - 表是否被自动建好？

3. 记录启动后的**第一屏**（原始 HTML 或截图）
```

### 1.3 同时准备"对照环境"

```
另复制一份，并把真实 data\fund_quant.db **复制**（不是移动）进去，同样启动。
两份环境分别用一个明确区分的方式记录（端口/目录名），不要混。
```

## 2. 旅程 A：零数据冷启动（主线，最重要）

在**空库**环境里，作为一个新用户，逐屏观察并记录。

### A2. 导航与信息架构
- 侧边栏/导航里有多少个入口？逐个点开
- 每个入口在空数据下表现如何？
- **新用户能否从界面上判断出：哪些功能现在不可用、为什么不可用、怎么让它可用？**

### A3. 冷启动路径
作为一个新用户，你的**第一个动作应该是什么**？
- 界面上有按钮能完成吗？还是必须去命令行？
- 如果需要命令行：**界面有没有告诉你**？（记录：官方文档 `README.md` / `docs/使用指南.md` 里写的启动步骤，与你在界面里看到的是否一致）

### A4. 数据采集（新用户的必经之路）

- 界面上有没有入口？没有的话，命令行命令是什么？
- **在本机网络环境下实际跑一遍**，记录：耗时、是否成功、失败在哪一步、报错原文
- 采集完成后**回到界面**：数字变了吗？变了哪些？
- **采集不完整时（例如净值只有几只）界面表现如何？**

### A5. 空状态的三态检查
对每个主要区块，确认是否具备三态：`加载中` / `空` / `有数据`。
- **缺哪一态？**（例如：一直在转圈 = 缺"空"态；直接显示数字 = 缺"空"态且更糟）

## 5. 数字自洽性交叉验证（黑箱，不用读码）

从界面上能看到的所有数字之间**必须互相自洽**。逐条验证并附原始数据：

1. **总资产 = 持仓市值 + 现金**（用接口返回的原始 JSON 核算）
2. **收益率 = 累计盈亏 / 累计成本**（自己算一遍，与界面显示对比）
3. **曲线最后一点 = 顶部 KPI 的当前市值**（不一致就是缺陷）
4. **曲线方向与盈亏方向一致**：如果盈亏为负，曲线不应表现为持续上行
5. **持仓明细逐只加总 = 汇总市值**（自己加一遍）
6. **已实现收益 + 浮动盈亏 与 总收益 是否对得上**（口径是否说明）
7. **同一指标在不同页面/不同接口是否一致**（例如"当前权益仓位%"在总览、调仓建议、计划卡三处）
8. **任何 `NaN` / `Infinity` / 空字符串 / `null` 出现在界面或接口里** —— 逐个记录位置

> 手法：调用接口拿原始 JSON，**自己用 Python 重算**，与界面显示的对比。差值超过四舍五入误差即记为【缺陷】。

## 6. 交易规则正确性黑箱验证

用**公开可查的基金页面**（天天基金等）作为独立事实来源，验证系统算得对不对。**不要读代码来"确认它是对的"**。

对以下每一条，给出"系统显示" vs "公开页面原文" 的对照：

### 6.1 确认周期
- 普通境内基金：`T 日 15:00 前提交 → 确认日 = T+1 交易日`
- **QDII 基金：`T 日提交 → 确认日 = T+2`**（例：`016453`）
- 15:00 后提交：顺延一天
- **周末提交**：按"周五收盘后下单"处理 → 生效日 = 下周一、确认日 = 下周二
- 逐个用**实际买入**验证（记录系统给的 `confirm_date`，与规则对照）

### 6.2 成交净值
- 系统用的成交净值，是否等于**生效日**当天的公开单位净值？
- 用公开净值独立核对（不要用系统自己的数据自证）

### 6.3 费率
- C 类份额申购费应为 **0**；赎回费 `<7 天 1.5%`、`≥7 天 0`
- 界面上成本/费用类数字是否与公开费率一致
- **买入/卖出后界面显示的"费用"金额**能否用公开费率手算复现

### 6.4 收益起算
- 界面/接口里的"收益起算日"是否符合规则（确认日当天净值更新后可看首笔盈亏）

> 每条给出：`规则原文（出处）` / `系统行为（原始输出）` / `是否一致`

## 7. 异常与边界（黑箱）

- **断网**：拔掉网络（或让出网失败）后打开各页面，记录：报错？转圈？显示旧数据？**有没有静默显示错数字？**
- **数据不全**：只采部分数据（例如只有 1 只基金净值），界面表现如何
- **并发**：同时打开两个标签页做同一操作，结果如何
- **刷新/多开**：反复刷新首页，数字是否稳定（有没有随机变化 = 缓存或计算不稳定）
- **超长等待**：记录每个端点的实际响应时间；**超过 10 秒的逐个列出**（新用户会以为卡死）
- **控制台**：记录浏览器 console 的报错（有的话，原文）
- **服务端日志**：记录启动到审计结束的全部异常栈

## 10. 特别提醒
