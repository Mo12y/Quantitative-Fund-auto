## 1. 设计语言（第 12 项）

### 1.1 参考项目定位（已通过搜索确认）

- **[Leonxlnx/taste-skill](https://github.com/Leonxlnx/taste-skill)** —— “给 AI 前端降降味”类项目，目标就是去掉生成式模板感（泛用渐变、玻璃拟态、emoji 堆砌、无意义圆角）。

- **[VoltAgent/awesome-design-md](https://github.com/VoltAgent/awesome-design-md)** —— 一批按流行品牌设计系统整理好的 `DESIGN.md`，丢进项目即可让编码代理生成风格统一的 UI。

### 1.3 拟落地方式（无论 A/B）

在仓库根新增 **`DESIGN.md`**（设计单一事实来源）+ 前端只从一份 **CSS 变量 token** 取值：

- **色彩**：中性色阶(背景/面板/边框/分隔) + 单一强调色 + 语义色(盈/亏/警示)；**取消**泛用紫蓝渐变、发光边框。
- **字体与层级**：一套清晰的字号阶（如 12/13/14/16/20/28），标题用**字重+字距**区分而非大写+emoji；数字统一 `tabular-nums`。
- **间距/圆角/描边**：4·8 基准间距；圆角 2 档（卡片 10、控件 6）；1px 描边为主，**不用阴影堆叠**。
- **组件规范**：按钮(present/ghost/danger)、标签、数据表、KPI 数字块、空态、Toast、表单。**统一去掉 emoji 当图标**（改为轻量 SVG 图标或纯文本标签）。
- **信息密度**：面向“专业看板”——表格化、右对齐数字、行高紧凑；避免大留白 + 大圆角卡片的“AI 落地页”观感。
- **一致性清单**：所有面板共享同一套 header/表格/空态；不出现“一个卡片一个风格”。

## 2. 数据层改造（SQLite 幂等迁移）

沿用现有 `Database.__init__` 里“建表 + `CREATE INDEX IF NOT EXISTS`”的幂等模式，**再加 `ALTER TABLE ADD COLUMN`（用 `PRAGMA table_info` 判断）**，老库自动升级、无需重建。

### 2.1 新增：交易日历

```sql
CREATE TABLE IF NOT EXISTS trade_calendar (
  trade_date TEXT PRIMARY KEY,   -- YYYY-MM-DD
  is_open    INTEGER NOT NULL    -- 1=交易日
);
```
- 来源：优先 akshare `tool_trade_date_hist_sina`，失败回退 `data/trade_calendar.csv`（由 `scripts/build_trade_calendar.py` 用 curl + 东方财富净值日期生成），再失败才回退“跳过周末”。
- 新增 CLI：`python src/main.py calendar`（刷新交易日历，建议每年/每月跑一次）。
  **注意：web 端没有日历按钮，`/api/calendar` 路由也不存在** —— 日历只能通过 CLI 刷新。
- 用途：**T+1 确认日**、**T+2 起算**、**定投跳过非交易日**。

### 2.2 扩展：持仓 `holdings`（T+1/T+2 状态机）

新增列（可空，兼容老数据）：

| 列 | 含义 |
|---|---|
| `apply_date` | 申请日（用户录入的日期） |
| `apply_after_cutoff` | 是否 15:00 后提交（0/1） |
| `confirm_date` | 确认日 = 申请日之后**第一个交易日**（15:00 前=下一交易日；15:00 后=再下一个） |
| `confirm_nav` | 确认净值（确认日当天的单位净值） |
| `accrual_start` | 收益起算日（= 确认日的下一交易日） |
| `status` | 扩展为 `pending_confirm` / `holding` / `sell_pending` / `sold` |

卖出（第 5 项“到账”）：**未在 `holdings` 上加列**。实际实现是把买卖双方都记进 `transactions`（`kind=buy|sell` + `apply_date/confirm_date/confirm_nav/accrual_start/shares/amount`），`holdings.status` 走 `pending_confirm → holding → sell_pending → sold`（部分卖出后仍为 `holding`，全部卖出才置 `sold`）。

> 兼容：老记录（无 apply 字段）按“`buy_date` 即申请日、`confirm_date=buy_date` 的下一交易日”补算一次。

### 2.3 新增：部分卖出流水 `transactions`（可选但建议）

当前 `holdings` 是“整条买入→整条卖出”。需求 5 的“部分卖出、到账”需要按**份额**记录。建议：
```sql
CREATE TABLE IF NOT EXISTS transactions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  holding_id INTEGER, kind TEXT,           -- buy|sell
  ts TEXT,        -- 申请时间
  trade_date TEXT, confirm_date TEXT, nav REAL, shares REAL, amount REAL,
  fee REAL DEFAULT 0, status TEXT
);
```
`holdings` 只存“当前持仓快照”（剩余份额/成本），`transactions` 存流水与待确认。

### 2.4 新增：投资计划持久化（第 1 项）

```sql
CREATE TABLE IF NOT EXISTS investment_plans (
  id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT, goal TEXT,
  total_capital REAL, cash_reserve REAL, start_date TEXT,
  horizon TEXT,          -- 计划周期，如 "6个月"
  risk_pref TEXT,        -- 风险偏好
  notes TEXT, status TEXT DEFAULT 'active',
  created_at TEXT, updated_at TEXT
);
CREATE TABLE IF NOT EXISTS investment_plan_items (
  id INTEGER PRIMARY KEY AUTOINCREMENT, plan_id INTEGER,
  fund_code TEXT, fund_name TEXT, role TEXT,
  target_amount REAL, target_pct REAL, cadence TEXT, notes TEXT
);
```
- 迁移：把现有 `investment_plan.py` 的常量**一次性 seed** 进去（保持当前计划不丢）。
- `investment_plan.py` 的 `get_plan()/get_progress()` 改为**读库**（保留旧签名，向后兼容）。

### 2.5 新增：定投期次 `dca_periods`（第 7 项对账基础）

```sql
CREATE TABLE IF NOT EXISTS dca_periods (
  id INTEGER PRIMARY KEY AUTOINCREMENT, plan_id INTEGER,
  period_no INTEGER, planned_date TEXT, planned_amount REAL,
  status TEXT,            -- pending|executed|skipped
  executed_date TEXT, holding_id INTEGER
);
```
- `dca_plans` 增列：`auto_sync INTEGER DEFAULT 1`、`last_synced_at TEXT`。
- 期数推算：从 `start_date` 起到今日，按频率取锚点日，**只数交易日**（`trade_calendar`）。

### 2.6 金额精度（第 6 项）

- 统一 2 位小数显示：`fmtMoney` 改为 `¥1,234.56`（千分位+两位），涨跌金额、成本、市值、每期金额全部走它。
- 入库仍存原始 float，**只在展示层格式化**，不引入新误差。

## 3. 业务规则（第 3、5、7 项的核心算法）

### 3.1 T+1 / T+2 确认规则

```
输入：apply_date（录入日期）、apply_time（15:00 前后）
若 apply_date 非交易日 → 顺延到下一个交易日作为「生效日」
15:00 前提交 → 确认日 = 生效日的下一个交易日
15:00 后提交 → 确认日 = 生效日之后的第二个交易日
confirm_nav = fund_nav[生效日]        ← 公募规则：按 T 日净值成交（**已实现**）
   ※ 修正：原设计写的是 fund_nav[confirm_date]（T+1 净值）且"缺失取最近一条"，
     两点都已在批次二改掉 —— 成交价用生效日，且**不再用邻近日兜底**。
accrual_start（收益起算日）= 确认日的下一个交易日
```
验收用例（M1 必测）：周五 15:00 前 / 周五 15:00 后 / 周六 / 周日 / 节前最后交易日 / 节后首日 → 确认日与起算日全部正确。

### 3.2 逐日累乘重算（第 3 项，解决“几天不开页面就偏”）

关键点：**不依赖“打开页面时才算”** —— `fund_nav` 里本来就有每一天的净值，所以任何时刻都能**从买入起算日到今天**完整重放：

```
份额 shares           = buy_amount / confirm_nav
逐日：nav_t（t 从 accrual_start 到最新交易日）
最新市值 = shares × nav_latest
累计收益 = shares × (nav_latest − confirm_nav)
累计收益率 = nav_latest / confirm_nav − 1
```
- 用**净值比值**而非“逐日收益率累乘”，避免 `daily_return` 列本身不可靠带来的误差（该列历史上有缺失）。
- 非交易日自然没有净值点，按“最近可用净值”前向填充。
- 刷新按钮：`POST /api/holdings/refresh` → 后端重放全部持仓 → 返回新市值/盈亏 + 每只的近 N 日净值序列（供曲线）。

### 3.3 组合曲线（第 13 项）

```
以“所有持仓 accrual_start 的最早日期”为起点，按日期并集（前向填充）
组合市值_t = Σ holdings  shares_i × nav_i(t)
组合收益_t = 组合市值_t − Σ(持仓成本_i)
```
在总览渲染“累计收益 / 资产净值”双线（或面积）。

### 3.4 定投期数与同步（第 7 项，按已确认语义）

```
应投期数 N = 从 start_date 到 today 的“计划锚点交易日”个数
已投期数 M = plan.total_periods
若 N > M：
  自动补录“最近一个已到期期次”（1 期，会生成一笔买入）
  其余 (N−M−1) 期 → 在页面显示“待补录”，提供「一键补录第 M+1…N 期」按钮（用户主动触发）
若 N == M：显示“已同步”
```
- 频次锚点：`daily`=每个交易日；`weekly`=每周固定星期（跳过节假日顺延）；`biweekly`=隔周；`monthly`=每月锚日。
- 每期买入的确认/起算同样走 §3.1 规则，逐期收益按 §3.2 计算。
- **周末/节假日不执行**（第 7 项明确要求）。

## 5. 前端结构（第 2、4、6、9、10、11、13 项）

- **局部刷新替代整页重载（第 2 项）**：加仓/减仓成功后，**只**重渲染「持仓明细 + 调仓建议 + 总览 KPI」这几块（`renderHoldings()`/`renderRebalance()`/`renderOverview()`），Toast 反馈，**不跳转、不 reload**；仅当需要重算重分析时才后台异步刷新。
- **每行曲线（第 4 项）**：持仓行内嵌 60 日 sparkline；点击展开更大曲线。
- **每行刷新（第 3 项）**：持仓区顶部「↻ 刷新净值」→ 调 `/api/holdings/refresh` → 局部更新行内金额与曲线。
- **第 9 项**：板块面板 Top 10 → **Top 20**，靠后 5 → **10**（后端已返回全榜单，纯前端）。
- **第 10 项**：量化模型改为**表+图并排、可折叠分组**，首屏只给“结论行”（最优模型/显著性），细节折叠。
- **第 11 项**：总览加“总资产 / 累计收益 / 收益率 / 持仓分布(环形或条形) / 行业占比 / 组合曲线”。
- **第 13 项**：总览顶部插入组合累计曲线（与第 11 项同区）。
- **第 6 项**：全局金额两位小数。
