fix(前端/阶段2对账): 补回重写时丢失的三处披露 + 温度精度口径统一

阶段 2「数字与旧前端逐项对账」的产出。做法：拉三个 API 抽出规范数字，
对照旧前端 / 与新前端 /v2 实际渲染的文本，专找「后端给了但界面没渲染」的字段
——这类缺失最难自查，因为界面看起来完全正常，只是少了披露。
脚本：scripts/recon_frontends.py

== 对账结果：数字本身全部一致，问题都在「少显示了什么」 ==

一致项：总资产 ¥854.51 / 累计收益 +¥1.62 (+0.19%) / 已实现 −¥30.71 (34笔·赎回费¥7.21)
        / 权益占比 33.90% vs 目标 36.90% / 曲线收益率 +0.20%

== 缺陷 1（最严重）：数据不足时会显示「0°」—— F-02 反模式被重写带回 ==

Today.tsx 原写 `Math.round(ov.temp.temperature)`，而 JS 里 **`Math.round(null) === 0`**。
后端在全部维度缺失时明确返回 `temperature = null`（thermometer.py:145），
于是界面会显示「**0°** 数据不足 · 数据不足，暂不给仓位建议」——
一个具体数字配一个「无数据」标签，还套着 ≤40 的冷色。
这正是黑箱验收审计 F-02 修掉的那个反模式（旧实现兜底成 50.0，让缺失伪装成中性读数）。
修：以 `insufficient_data` / `temperature == null` 为准显示「数据不足」，
并且**不画温度条**（画一条 0% 的条同样是"假装有读数"）。

同类缺陷的教训：**这已是本项目第二次栽在「缺失值伪装成具体数字」上**，
且两次都发生在前端兜底处。后端已经做对了（返回 null 而不是 50.0），
兜底压力全在前端——写前端展示时必须把 null 当一等公民。

== 缺陷 2：估值分化告警整段丢失（安全披露） ==

后端一直在给 `temp.divergence.level`（'轻微分歧'）与 `.message`
（'估值信号有分歧，建议结合其他信息判断'），旧前端也一直显示，
但重写时**整个漏掉了**。这不是装饰——系统在说"我的几个估值信号互相矛盾，
别过度相信这个读数"，而界面装作没这回事。与 F-02 属同一类问题。
修：divergence 非「一致」时以警示色渲染。

== 缺陷 3：曲线「未入仓」披露丢失 —— F-03 修复成果归零 ==

曲线只画「已起算」持仓，于是曲线终值与顶部 KPI「总资产」天然对不上
（本机实测 KPI ¥854.51 vs 曲线 ¥834.60）。审计 F-03 专门修过这个
「同一屏两个市值互相打架」，修法就是**把差额显式说出来**，
后端为此加了 excluded_not_in / excluded_pending / excluded_amount。
但重写时**三个字段一个都没渲染**：types.ts 里声明了类型，全项目无人使用
（grep 只命中类型定义本身）。用户会重新看到两个对不上的数字而无从解释。
修：CurveChart 渲染「另有 N 笔未入仓（约 ¥X）未计入」，措辞与旧前端一致。

== 修复 4：温度精度口径统一（原为只显示整数） ==

原用 Math.round 显示整数，有两个问题：
  ① **与阈值判定不一致**：取色分档是 40/60/80，后端 level_desc 也按未取整值算。
     显示「60°」却套着 >60 的警示色 / 写着「偏热」——用户看到的数
     与系统的判断依据不是同一个数。
  ② **与旧前端不一致**：旧前端显示 46.2°，新前端 46°。计划书 §7 阶段 4 要求
     两套界面对照跑至少两周，这期间数字不同会削弱信任，也会掩盖真实差异。
改为 1 位小数（后端 `thermometer._r()` 的实际精度就是 round(v,1)，不是伪精度）。
五维分位同样改为 1 位小数。

== 顺带修：硬编码的「起止 0.00%」 ==

文案里写死数字迟早与实际不符；且「起止」指首尾两个值却只给了首值，措辞与内容不符。
末值已由大字号主结论显示，故改为只报「起点 −0.08%」交代基线。
