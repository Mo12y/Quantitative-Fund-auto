## 2. 新发现：Sharpe 存在单位错配，风控利率形同虚设（HIGH）

### 2.1 问题

`src/analysis/backtest.py`：

```python
78: def compute_metrics(returns: np.ndarray, rf_annual: float = 0.02) -> Dict:
83:         returns: 月收益数组，单位 %          # ← 百分数
84:         rf_annual: 无风险利率（年化）        # ← 未标注单位
92:     ann_ret = ((nav[-1]) ** (12.0 / n) - 1) * 100     # ← 结果是百分数，如 12.86
93:     ann_vol = np.std(r, ddof=1) * np.sqrt(12)         # ← 也是百分数，如 10.89
94:     sharpe = (ann_ret - rf_annual) / ann_vol          # ← 12.86 − 0.02
```

`ann_ret` 是**百分数（12.86）**，而 `rf_annual` 传的是**小数（0.02）**。扣掉的是 0.02 个百分点，而不是 2 个百分点 —— **差 100 倍，无风险利率实际上没被扣**。

### 2.2 实测

```
$ python v3_sharpe.py
   rf_annual=0.0    -> annual_return= 12.86  annual_volatility= 10.89  sharpe=  1.18
   rf_annual=0.02   -> annual_return= 12.86  annual_volatility= 10.89  sharpe=  1.18   ← 完全没变
   rf_annual=0.2    -> ... sharpe=  1.16
   rf_annual=2.0    -> ... sharpe=   1.0    ← 这个量级才对
   rf_annual=20.0   -> ... sharpe= -0.66

手算 ann_ret=12.8562%  ann_vol=10.8863%
正确 Sharpe (rf=2%)   = 0.9972
错配 Sharpe (rf=0.02) = 1.1791  ← compute_metrics 的实际行为
```

`rf_annual` 从 `0.0` 改到 `0.02`，Sharpe **变化 0.0000**（正确应为 2.0/10.89 = 0.1836）。

### 2.3 更麻烦的是：另一个模块口径相反，且自称"同口径"

`src/analysis/vol_predictor.py`：

```python
880: def _portfolio_metrics(monthly_rets, rf_annual=0.02):
881:     """... （Sharpe 扣无风险利率，与 backtest.compute_metrics 同口径）"""   # ← 这句话是假的
886:     nav = np.cumprod(1 + r)              # r 是**小数**
888:     ann_ret = nav[-1] ** (12 / n) - 1    # ← 小数，如 0.1286
890:     sharpe = (ann_ret - rf_annual) / ann_vol    # 0.1286 − 0.02 → 正确
```

- `_portfolio_metrics`：收益是**小数**，`rf=0.02` → **计算正确**，Sharpe ≈ 0.997
- `compute_metrics`：收益是**百分数**，`rf=0.02` → **计算错误**，Sharpe ≈ 1.179

**同一策略在两个模块会报出 1.18 与 0.997 两个不同的夏普**，而 docstring 声称二者同口径。

### 2.4 影响

1. 历史回测/ML 报告里所有 Sharpe **被系统性高估**，幅度 = `rf / ann_vol`。以年化波动 10.9% 计约 **+0.18**；波动越低高估越多（年化 5% 时高估 +0.4）。
2. 两个模块口径不一致，跨模块对比无意义。
3. **次要**：`compute_metrics` 的 `total_return`/`annual_return` 返回**百分数**，`_portfolio_metrics` 返回**小数**（`0.1286`）。请一并核查报告格式化层是否对两者做了正确区分（`fmt_pct` vs `fmt_num`），否则存在"12.86"与"0.1286"混排的风险。

### 2.5 建议修法

让 `rf_annual` 保持**小数语义**（行业惯例），在减法前把百分数指标归一化：

```python
sharpe = ((ann_ret - rf_annual * 100) / ann_vol) if ann_vol > 0 else 0
```

并在 docstring 明确 `rf_annual: 小数（0.02 = 2%）`。这样调用方无需改动，且两个模块口径真正统一。

**必配测试**：
- `rf_annual=0.0` 与 `rf_annual=0.02` 的 Sharpe 差必须等于 `0.02*100/ann_vol`（回归这个 bug）
- `compute_metrics` 与 `_portfolio_metrics` 对**同一组收益**（各自单位正确）算出的 Sharpe 必须一致

### 3.3 【P3】TradingAgents 的时点隔离纪律 —— 借鉴理念，不引依赖

# 上界是「end 之后那天午夜」的**开区间**，正好卡在午夜的文章不会漏进来

### 2.3 修 `ms_to_date` 的机器时区依赖

**位置**：`src/data/hithink_collector.py:417-423`

```python
@staticmethod
def ms_to_date(ms: int) -> str:
    """毫秒时间戳 → 日期字符串"""
    try:
        return datetime.fromtimestamp(ms / 1000).strftime("%Y-%m-%d")
```

**问题**：`datetime.fromtimestamp()` 使用**本机时区**。同花顺返回的是**北京时间零点的毫秒**（实测 `1788451200000` → 北京 `2026-09-04 00:00`）。

实测本机为 UTC+8，所以现在**恰好正确**；但部署到 UTC 服务器（或 Docker 默认 UTC）时，**所有净值日期会整体早一天** —— 直接污染 T+1 计价与 `effective_apply_date`。

这与 TradingAgents 记录过的同类问题一致（其 `#1126`：*host-local timestamp parsing made filtering machine-dependent*）。

**要求**：显式指定时区，不依赖机器设置。
```python
from zoneinfo import ZoneInfo
_CN = ZoneInfo("Asia/Shanghai")
return datetime.fromtimestamp(ms / 1000, tz=_CN).strftime("%Y-%m-%d")
```

**验收测试（必须新增）**：
- 断言 `ms_to_date(1788451200000) == "2026-09-04"`
- **在 `TZ=UTC` 环境下运行同一测试，必须仍返回 `"2026-09-04"`**（这是回归此 bug 的关键）

**问题**：`after_cutoff`（15:00 后）是**交易日专有概念** —— 非交易日根本没有 15:00 下单这件事。但代码在"非交易日顺延"之后**又叠加了一次** cutoff 顺延。

### 5.2 【中】买入份额公式：隐含假设"申购费 = 0"

**位置**：`src/analysis/portfolio.py:421`（及 `:134`、`:177`、`:485`）

```python
shares = round(amount / confirm_nav, 2)
```

**权威口径（D1 页面原文）**：
```
净申购金额 = 申购金额 / (1 + 申购费率)
申购费用   = 申购金额 - 净申购金额
申购份额   = 净申购金额 / T日基金份额净值
```

**现状影响**：
- **C 类（申购费 = 0）**：`净申购金额 = 申购金额` → 代码**恰好正确** ✅（用户 7/7 持仓均为 C 类）
- **A 类（申购费 > 0）**：正确份额 = `amount/(1+fee)/nav`，代码给 `amount/nav` → **份额高估** `fee/(1+fee)`（1.5% 费率 → 高估约 1.48%）
- 且买入路径**完全不记录申购费**（`transactions.fee` 买入时为 0）

**要求**：
1. 买入改为按上式：`net = amount / (1 + purchase_rate)`，`shares = round(net / nav, 2)`，并**记录 `申购费用`** 到 `transactions.fee`
2. 申购费率来源：**份额类别**（C 类 0）+ 真实前端费率（属《数据源扩展计划书》阶段 1）
3. **对存量 C 类记录**：因费率为 0，结果不受影响，**无需回填**

**验收测试**：
- C 类（费率 0）→ 结果与现值**完全一致**（防回归）
- A 类（费率 1.5%）→ 断言 `shares == round(amount/1.015/nav, 2)`
- 断言 `transactions.fee` 记录了申购费用
