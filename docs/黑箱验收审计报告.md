## 9. 附录：事后读码定位（仅用于解释 §3 已记录的现象）

> 本节在全部发现记录完毕后才阅读源码，仅用于定位根因。

### 复现抽查（任务书 §10.5：挑最严重的 3 条重走一遍）

| 发现 | 第一次取证 | 复现验证 | 结论 |
|---|---|---|---|
| **F-02**（兜底温度 50.0） | 空库首屏（19:33） | 跑完 init 后（20:0x）再读 `/api/all` → `temperature=50.0`、`components` 仍全 `null` | ✅ 两次一致 |
| **F-08**（跑完文档流程界面不变） | init 前 `/api/funds total=0` | init 后（18m28s）+ 重启 Web → 仍 `total=0`、`source=cache` | ✅ 两次一致 |
| **F-04**（假代码入库） | 表单提交 `999999` → holdings 28→29 | 后续所有 `/api/all` 读取中该记录持续存在（id=78, ¥100.00） | ✅ 稳定复现 |

- **A1（F-01 根因）**：`src/analysis/investment_plan.py` 把计划**硬编码**在源码里（README §数据与隐私已承认：
  "把投资计划硬编码在源码里，包含真实基金代码、金额、日期"）。`/api/all` 的 `plan` 段直接返回该常量，
  与 `holdings` 是否为空**无关**；`stats.cash_reserve/total_assets` 也直接取该计划的 `cash_reserve`。
- **A2（F-02 根因）**：`src/analysis/thermometer.py` 的 `get_temperature()`：
  ```python
  total_w = sum(self.weights[w] for w, _ in used)
  if total_w > 0:
      temperature = sum(self.weights[w] * v for w, v in used) / total_w
  else:
      temperature = 50.0                     # ← 全部维度缺失时的兜底
      degraded = [w for w, _, _ in dims]
  level, level_desc, action, _ = self._classify_temperature(temperature)   # 照样给出"适中/保持定投"
  ```
  **讽刺之处**：同一文件在成交量维度上明确写着「无数据/样本不足时返回 None…**绝不返回 50.0 —— 那会让"数据缺失"伪装成一个中性的真实读数**」，
  但**顶层兜底恰恰做了这件事**：`total_w == 0` 时仍产出 50.0，并继续走档位分类与仓位插值（35%）。
- **A3（F-03 根因）**：`PortfolioTracker.get_portfolio_curve()`（`src/analysis/portfolio.py`）只把
  `status != 'pending_confirm'` 且 `shares > 0` 的持仓纳入曲线，并按各自 `accrual_start` 起算，
  日期轴取所有持仓净值日期的**并集**；而 `stats.total_market_value` 汇总的是**全部持仓**的
  `current_value`（含起算日在曲线末日之后的 4 笔）。两者口径不同 → 末点必然不等。
- **A4（F-04 根因）**：买入路径**只有前端一道校验**，且只判"非空 + 金额 > 0"——
  `src/web/static/app.js:169`：
  ```js
  if(!code||!amount||amount<=0){toast('请填写基金代码和大于0的金额',false);return;}
  ```
  后端 `/api/holdings`（`src/web/app.py`）按 `action` 分发，未对 `fund_code` 做**存在性校验**
  （未查 `fund_info`），因此 `999999` 直接落库为 `pending_confirm` 并计入 `total_invested/total_market_value`。
  另：同一处 `return jsonify({"ok": False, "error": f"未知操作: {action}"})`（app.py:903、1106、1245）
  解释了几何 E-04 的空值拼接文案。
- **A5（F-06 根因）**：`src/cli/data_cmds.py` 的 `cmd_init()` 顺序是
  `cmd_test() → cmd_collect() → cmd_nav() → cmd_enrich()`，**不含 `cmd_calendar()`**；
  而 `calendar` 是独立命令（README「日常命令」/帮助里才列）。因此"一键初始化"永远补不上交易日历。
- **A6（F-07 根因）**：`cmd_nav()` 的计数是
  ```python
  try:
      df = collector.collect_fund_nav(code)
      collector.save_fund_nav_batch(code, df)   # 内部 records 为空则不 insert
      success_nav += 1                          # ← 只要没抛异常就算"成功"
  except Exception:
      fail_count += 1
  ```
  而 `save_fund_nav_batch()` 对空/异常格式的返回**不写任何行**。于是"600 只 ok"统计的是
  **接口调用未抛异常**，不是**实际入库只数**（实测 600 → 305）。

- **A7（F-08 根因，黑箱内可定位的部分）**：`analysis_snapshot` 表里 `funds` 这个 key 缓存的是
  `{"funds": [], "summary": {"total": 0, ...}}`（空结果），而 `/api/funds` 一直返回 `source: "cache"`。
  同一时刻库里 `fund_nav` 有 **296 只**基金的净值天数 ≥250 天。
  → 采集完成后**缓存没有被失效/重算**，界面就一直端着那份空快照；
  至于是"缓存未失效"还是"筛选条件把 296 只全滤掉"，**黑箱内无法进一步区分**（见 §7）。
  页面右上角虽有「重算数据」按钮，但点击后 `/api/funds` 仍返回 `source=cache`（点击是否真正触发重算未验证）。
